# 취업 면접 연습실 개발명세서

작성일: 2026-10-17. 상태: 문답 기반 초안. 앱 제작·외부 서비스 생성·배포는 아직 수행하지 않았다.

## 1. 기본 정보
프로젝트명은 ‘취업 면접 연습실’(가칭)이다. 특성화고·마이스터고 학생이 지원 직무와 경험을 바탕으로 면접 질문을 확인하고 답변을 연습하며, 교사가 지도하는 반응형 웹앱이다. 질문 준비부터 답변 수정까지 한 곳에서 진행하는 것이 목적이다. 첫 버전의 성공 기준은 가상 학생으로 질문 확인 → 답변 작성 → 예시 피드백 → 답변 수정 → 교사 의견 확인 → 인쇄 흐름이 완주되는 것이다.

## 2. 사용자
- 학생: 자신의 가상 프로필, 질문, 답변, 피드백과 교사 의견 확인 및 답변 수정.
- 담당 교사: 담당 가상 학생의 진행 현황과 답변 조회, 지도 의견 작성. 학생 답변은 직접 수정하지 않는다(가정).
- 별도 관리자 화면은 첫 버전에서 제외한다(가정).

## 3. 환경
학생은 휴대폰, 교사는 PC 브라우저를 주로 사용한다. 설치 없는 반응형 웹앱이며 초기 접속은 네트워크가 필요하다. 오프라인 설치·동기화는 범위 밖이다. 최신 주요 브라우저를 대상으로 하며 구체 버전은 구현 시 확인한다.

## 4. 시나리오
- 학생: 데모 학생 선택 → 간단 입력 또는 가상 자기소개서 선택 → 질문 자료 확인 → 답변 입력 → 준비된 피드백 확인 → 수정·저장 → 인쇄. 필수값 누락은 입력 근처에서 안내하고 내용을 보존한다.
- 교사: 교사 체험 → 담당 학생 선택 → 답변과 수정 이력 확인 → 의견 저장. 담당 외 가상 학생은 목록과 상세 경로에서 접근을 거부한다. 이 처리는 체험용이며 실제 보안 경계가 아니다.
- 복구: 저장 오류 시 입력은 화면에 남기고 재시도·텍스트 복사를 제공한다. 손상된 저장 자료는 자동 삭제하지 않고 초기화 선택을 제공한다.

## 5. 사용자 흐름
시작 화면 → 학생/교사 체험 선택 → 해당 역할 홈. 학생 홈 → 지원 정보 → 질문 자료 → 연습 → 피드백·수정 → 기록. 교사 홈 → 담당 학생 → 연습 상세 → 지도 의견. 학생 기록에서 의견 확인과 인쇄로 이어진다.

## 6. MVP 범위
확정: 간단 입력과 자기소개서 방식, 질문·꼬리 질문·답변 요령, 답변 연습과 피드백, 학생별 기록, 교사 지도, 인쇄, 학교 서비스형 디자인, 가상 데이터 및 준비된 결과.

시제품 가정: 실제 로그인 대신 역할 체험, 같은 브라우저의 로컬 저장, 예시 데이터 선택과 직접 입력 병행. 직접 입력은 기록에 반영하지만 질문·피드백은 직무별 준비 데이터에서 선택한다. 입력 내용을 AI가 분석한다고 표시하지 않는다.

후속: 실제 로그인, 중앙 저장과 기기 간 공유, 실제 AI 분석. 제외: 음성·영상 녹화, 합격 확률, 채용 결정·학생 순위, 실제 학생 자료, 파일 업로드, 실제 기업의 최신 기출 보장.

## 9. 디자인
사용자가 선택한 밝은 배경·파란색·단정한 학교 서비스형을 반영한다. 기존 DESIGN.md는 제공되지 않아 동봉 초안을 사용한다. 참고 링크는 ‘면접ON’의 공개 제목과 소개만 확인했으며 교사 인증으로 내부 화면·기능은 확인하지 못했다. 복제 명세가 아니다. 학생은 한 번에 한 질문, 교사는 목록과 상세 중심으로 조정한다. 구체 색상·간격은 DESIGN.md의 가정이다. 다크 모드는 제외한다.

## 10. 데이터
저장: 가상 프로필, 지원 정보, 질문 묶음, 답변 버전, 예시 피드백 식별자, 교사 의견, 수정 시각. 실제 개인정보·비밀번호·API 키는 수집하지 않는다. 데모 사용자가 작성·수정하며 초기화로 앱 자료 전체를 삭제할 수 있다. 로컬 자료는 초기화 또는 브라우저 저장소 삭제까지 남는다. 서버 백업은 없고 기기 간 공유도 없다.

## 11. 데이터 모델
실제 DB 없이 타입이 있는 객체와 앱 전용 localStorage를 사용한다. 스키마 버전을 포함한다.

| 엔터티 | 주요 필드(별도 표시 외 필수) | 관계 |
|---|---|---|
| DemoUser | id:string(고유), role:student/teacher, displayName:string, teacherId?:string | 교사 1:N 학생 |
| Application | id:string(고유), studentId:string, mode:basic/essay, company?:string, job:string, experiences?:string, essay?:string | 학생 1:N 지원 |
| QuestionSet | id:string(고유), applicationId:string, templateJob:string, questions:Question[] | 지원 1:N 질문 묶음 |
| Question | id:string, category:string, text:string, followUps:string[], guidance:string, feedbackExample:string | 묶음 내부 ID 고유 |
| Answer | id:string(고유), studentId:string, questionSetId:string, questionId:string, versions:{text:string,createdAt:string}[] | 질문 1:N 버전 |
| TeacherComment | id:string(고유), teacherId:string, answerId:string, text:string, updatedAt:string | 답변 1:N 의견 |

예: 학생 demo-s01 ‘가상학생 A’, 교사 demo-t01 ‘체험교사’, 기업 ‘가상전자’, 직무 ‘설비보전’. 기본 데이터는 가상 학생 3명, 교사 1명, 생산·전기/설비·사무 직무별 질문 8개로 구성한다(수량·직무 가정). 초기화는 연관 레코드를 모두 초기 데이터로 되돌린다. 시제품 입력은 가상 자료만 허용한다는 안내를 지속 표시한다.

## 12. 시스템 구성
시제품은 브라우저 UI → 로컬 자료 처리 계층 → 예시 JSON/localStorage로 충분하다. 화면 코드와 저장·질문 제공 코드를 분리한다. 실제 학생·교사 간 기기 공유에는 인증된 서버와 중앙 DB가 필요하다. 역할 전환만으로 운영 서비스의 권한을 구현했다고 간주하지 않는다.

## 13. API·외부 서비스
시제품에는 외부 AI·인증·분석·파일 저장 API가 없다. 내부 모듈은 loadDemo, saveAnswer, getQuestionExamples, getFeedbackExample, saveTeacherComment로 구분한다. 저장 오류를 호출 화면에 반환한다. 후속 AI 연결은 서버 호출, 비밀키 보호, 전송 항목·보관 조건·비용 상한·오류 대응을 결정한 뒤 진행한다.

## 14. 로그인·권한
실제 회원가입·비밀번호·재설정·세션은 해당 없음. 체험 사용자 선택만 제공하며 역할 전환 시 화면의 미저장 수정 여부를 안내한다. 데모 조회 함수도 학생 ID와 담당 관계를 확인한다. 실제 버전에서는 학생 본인 자료, 담당 교사의 담당 학생 자료만 서버에서 허용해야 한다. 운영 관리자 범위와 학교별 분리는 미결정이다.

## 16. 개인정보·보안
시제품: 가상 정보만 기기에 저장, 외부 전송 없음. 입력 문장을 HTML로 실행하지 않고 텍스트로 표시한다. URL·로그에 답변을 넣지 않는다. 이미지·녹음·실제 학생 파일은 받지 않는다.

실사용 전 확인 조건: 학교 담당자가 최소 수집 항목, 학생 안내·동의 등 필요한 절차, 담당 교사 권한, 저장 지역, 보관 기간, 삭제·백업 정책, 외부 AI 제공·보관 조건을 정해야 한다. 확인 전 실제 학생 자료 입력·AI 전송을 활성화하지 않는다. 보관 기간은 임의로 확정하지 않는다. 개발 중 서버 권한 검증·입력 검증·비밀키 보호를 구현하고, 배포 전 타 학생·학급 접근 거부와 삭제·복원을 검증한다. 담당자는 미정이다. 이 문서는 위험 발견과 요구사항 정리이며 법률 검토·기관 승인·전문 보안 감사를 대체하지 않는다.

## 17. 기술 스택 제안
가정 기반 제안: React + TypeScript + Vite, CSS, localStorage. 화면·타입·예시 데이터 모듈을 분리하기 쉽고 서버 계정 없이 시제품을 실행할 수 있다. 난이도는 중간이다. 더 단순한 대안은 HTML/CSS/JavaScript이며 시작은 쉽지만 다중 화면·기록 관리가 커지면 유지보수가 어려워진다. 서버·인증·DB·파일 저장소·UI 라이브러리는 첫 버전에서 필요 없다. 검증은 브라우저 흐름 점검과 저장·데이터 분리 핵심 테스트를 사용한다. 특정 최신 버전·가격·서비스 정책은 확정하지 않으며 설치 시 공식 자료로 확인한다.

## 18. 배포·운영
우선 로컬 개발 서버에서 체험한다. 공개 배포·계정 생성·도메인 구매는 별도 요청 범위다. 추후 정적 호스팅을 검토할 수 있다. API 비용은 없으며 호스팅 비용은 선택 서비스에 따라 확인한다. 유지보수 담당자는 미정. 초기화로 기본 자료를 복원하고 데이터 형식 변경 시 버전 검사와 안내를 제공한다.

## 19. 검증 계획
아래 인수 조건을 수동 흐름으로 확인하고, 버전 저장·사용자 분리·잘못된 저장 데이터 처리에는 핵심 자동 검증을 둔다. 모바일 360px, 교사 PC 1280px, 키보드·확대·인쇄 미리보기, 네트워크에서 외부 AI 요청 없음도 확인한다. 실제 인증 보안 검증 완료로 보고하지 않는다.

## 22. 위험과 대응
고정 피드백을 AI 평가로 오해할 수 있으므로 ‘준비된 피드백 예시’를 항상 표시한다. 데모 역할 선택을 인증으로 오해하지 않도록 체험임을 표시한다. 로컬 저장 손실은 안내·인쇄로 대응하며 영구 보관을 약속하지 않는다. 실제 기출·합격 가능성으로 표현하지 않는다. 기능 확대는 로그인·AI 등 후속 단계로 분리한다.

## 23. 확정·가정·미결정
확정: 대상, 두 입력 방식, 자료·연습, 교사 지도, 가상 데이터, 예시 결과, 학생 휴대폰·교사 PC, 밝은 파란색 디자인.
가정: 가칭, 직무 3종·질문 8개씩, 가상 학생 3명, 역할 체험과 같은 브라우저 로컬 저장, 댓글형 교사 지도, 텍스트 입력·브라우저 인쇄, 제안 기술과 디자인 수치.
후속 결정: 실제 학교·계정·교사 배정, 보관 기간, 서버·AI 제공자, 예산·담당자·배포 환경. 시제품을 막는 미결정은 없다.

## 24. 쉬운 요약
학생은 가상 취업 자료로 질문을 확인하고 답변을 연습한다. 교사 화면에서는 학생 답변에 의견을 남긴다. 첫 버전은 준비된 예시로 체험하며 같은 브라우저에 기록한다. 실제 휴대폰과 교사 PC 사이 자료 공유는 후속 서버 연결이 필요하다.

## 25. 선택 이유
웹은 설치 없이 휴대폰·PC를 함께 지원한다. 시제품은 외부 서비스 없이 화면과 지도 흐름을 검증할 수 있다. 실제 서비스는 로그인·중앙 DB·서버 권한 검사가 필요하며 시제품 구조와 구분한다. 디자인은 읽기 쉬운 학교 도구를 목표로 한다.
