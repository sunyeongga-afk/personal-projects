# 아키텍처 판단 가이드

## 실행 플랫폼 결정

사용 환경을 질문한 뒤 다음 플랫폼 중 적절한 것을 판단한다.

- 웹앱
- 설치형 웹앱(PWA)
- Windows 프로그램
- Android 앱
- iOS 앱
- Android와 iOS를 함께 지원하는 크로스플랫폼 모바일 앱
- Windows와 macOS 등을 지원하는 크로스플랫폼 데스크톱 앱

플랫폼별 의미를 쉬운 말로 설명한다.

- 웹앱: 브라우저에서 주소로 접속한다. 설치 부담이 적고 여러 종류의 기기에서 사용하기 좋다.
- PWA: 웹앱을 일부 기기에서 앱처럼 설치할 수 있다. 제한적인 오프라인 기능이 필요할 때 고려한다.
- Windows 프로그램: Windows PC에 설치한다. 프린터, 로컬 파일, 특정 Windows 기능과 긴밀하게 연결할 때 유리할 수 있다.
- Android 앱: Android 휴대전화나 태블릿 중심으로 사용할 때 적합하다.
- iOS 앱: iPhone이나 iPad 중심으로 사용할 때 적합하다.
- 크로스플랫폼 모바일 앱: 하나의 코드 기반으로 Android와 iOS를 함께 지원할 때 고려한다.
- 크로스플랫폼 데스크톱 앱: Windows와 macOS 등을 함께 지원해야 할 때 고려한다.

다음 조건을 실제 사용 상황으로 질문한다.

- 주로 사용하는 기기의 종류
- 학교 기기의 운영체제
- 개인 기기 사용 가능 여부
- 프로그램 설치 권한
- 인터넷 연결 상태
- 학교 내부망에서만 사용해야 하는지
- 앱스토어 배포가 필요한지
- 카메라, 알림, GPS 또는 블루투스가 필요한지
- 프린터나 로컬 파일을 직접 사용해야 하는지
- 오프라인 사용이 필요한지
- 여러 종류의 기기를 동시에 지원해야 하는지

사용자가 플랫폼을 결정하지 못하면 다음 형식으로 비교한다.

- 권장 플랫폼
- 권장 이유
- 더 단순한 대안
- 대안이 더 적합해지는 조건
- 개발 및 배포 난이도 차이

## 프론트엔드와 백엔드 구성 판단

사용자에게 “프론트엔드와 백엔드 중 무엇을 원하나요?”라고 직접 묻지 않는다.

다음과 같은 실제 필요를 질문한다.

- 입력한 내용을 현재 기기에만 저장해도 되는가?
- 다른 컴퓨터나 휴대전화에서도 같은 자료를 불러와야 하는가?
- 여러 사람이 같은 자료를 보거나 수정해야 하는가?
- 회원가입이나 로그인이 필요한가?
- 사용자마다 자신의 자료만 보여야 하는가?
- 교사, 학생, 관리자마다 권한이 달라야 하는가?
- 데이터가 사라지지 않도록 중앙에서 보관해야 하는가?
- 이메일, 문자 또는 푸시 알림을 보내야 하는가?
- AI, 지도, 결제 또는 학교 시스템과 연결해야 하는가?
- 외부 서비스의 비밀 API 키를 보호해야 하는가?
- 여러 사용자의 작업을 실시간으로 동기화해야 하는가?

다음 기준으로 판단한다.

프론트엔드 중심 구현이 가능한 경우:

- 정적인 자료를 보여주는 프로그램
- 간단한 계산이나 변환 도구
- 한 사람이 한 기기에서 사용하는 도구
- 로컬 저장만으로 충분한 경우
- 계정, 권한, 공유, 중앙 저장이 필요 없는 경우

백엔드가 필요한 가능성이 높은 경우:

- 로그인과 회원 관리가 필요한 경우
- 여러 사용자의 자료를 중앙에서 저장하는 경우
- 여러 기기에서 같은 자료를 불러오는 경우
- 교사, 학생, 관리자 권한이 구분되는 경우
- 공동 작업이 필요한 경우
- 외부 API의 비밀키를 보호해야 하는 경우
- 이메일, 알림, 예약 작업 등을 서버에서 처리하는 경우
- 데이터 백업과 복구가 중요한 경우

판단 결과는 다음 형식으로 설명한다.

- 판단: 프론트엔드만으로 가능 / 백엔드 필요 / 프론트엔드로 시작 후 확장 가능
- 판단 근거
- 가장 단순한 구현 방법
- 확장할 때 달라지는 부분
- 개인정보와 보안에 미치는 영향

소규모 연수용 시제품은 로컬 저장 또는 관리형 백엔드 서비스를 이용해 복잡성을 줄이는 방법도 고려한다.

## 데이터 저장 방식 결정

처음부터 SQL과 NoSQL 중 하나를 선택하라고 요구하지 않는다.

먼저 다음 내용을 질문한다.

- 어떤 정보를 저장해야 하는가?
- 정보들이 서로 어떤 관계를 가지는가?
- 한 사용자가 여러 학급이나 과제를 가질 수 있는가?
- 학급–학생–과제–제출물처럼 연결되는 구조가 있는가?
- 점수, 출결 또는 제출 기록처럼 정확성이 중요한가?
- 통계, 검색, 정렬, 집계 또는 보고서가 중요한가?
- 게시글이나 문서처럼 한 덩어리의 자료를 저장하는가?
- 저장되는 항목의 구조가 자주 달라지는가?
- 실시간 데이터 변경이 중요한가?
- 데이터 수정 기록이나 감사 기록이 필요한가?
- 예상되는 사용자 수와 데이터 양은 어느 정도인가?
- 백업과 복구가 필요한가?

다음 기준으로 저장 방식을 판단한다.

## 로컬 저장소 또는 파일

다음 조건에서 고려한다.

- 한 사람이 한 기기에서 사용한다.
- 데이터가 적다.
- 여러 사람과 공유할 필요가 없다.
- 민감한 정보를 저장하지 않는다.
- 로그인이 필요하지 않다.
- 데이터 손실 위험을 감수할 수 있다.

## 관계형 데이터베이스

다음 조건에서 우선 고려한다.

- 사용자, 학급, 과제, 제출, 평가처럼 정보 사이의 관계가 명확하다.
- 데이터의 정확성과 일관성이 중요하다.
- 중복 데이터를 줄여야 한다.
- 통계, 검색, 정렬, 보고서가 중요하다.
- 출결, 성적 또는 결제처럼 여러 변경을 안전하게 처리해야 한다.
- 사용자와 권한 구조가 명확하다.

관계형 구조가 자연스러운 프로젝트에는 관계형 데이터베이스를 기본 선택으로 고려한다.

## NoSQL 데이터베이스

다음 조건에서 고려한다.

- 문서 구조가 유동적이고 자주 달라진다.
- 각 자료가 독립적인 문서 형태다.
- 특정 실시간 동기화 기능이 핵심이다.
- 관리형 서비스의 문서형 구조가 시제품 제작에 적합하다.
- 관계형 구조보다 문서 중심 구조가 자연스럽다.

유행이나 막연한 확장성을 이유로 NoSQL을 추천하지 않는다.

## 관리형 백엔드 또는 BaaS

다음 조건에서 고려한다.

- 개발자가 초보자이거나 개발 인력이 적다.
- 로그인, 데이터베이스, 파일 업로드를 빠르게 구현해야 한다.
- 직접 서버를 관리하기 어렵다.
- 소규모 서비스 또는 시제품이다.

데이터베이스가 필요 없는 프로젝트에는 데이터베이스를 억지로 추가하지 않는다.

판단 결과는 다음 형식으로 설명한다.

- 추천 저장 방식
- 추천 이유
- 데이터 구조 예시
- 장점
- 주의점
- 다른 방식이 더 적합해지는 조건

## 로그인과 사용자 권한 판단

다음 사항을 필요에 따라 확인한다.

- 로그인이 반드시 필요한가?
- 계정 없이 사용할 수 있는가?
- 교사, 학생, 학부모, 관리자 역할이 구분되는가?
- 역할에 따라 볼 수 있는 정보가 달라지는가?
- 역할에 따라 수정할 수 있는 정보가 달라지는가?
- 학교 계정, Google 계정 또는 Microsoft 계정으로 로그인해야 하는가?
- 관리자가 계정을 생성하거나 승인해야 하는가?
- 비밀번호 재설정이 필요한가?
- 학교나 학급 단위로 자료를 분리해야 하는가?
- 계정을 비활성화하거나 삭제할 수 있어야 하는가?

로그인이 필요 없는 프로젝트에는 불필요한 인증 구조를 추가하지 않는다.

## 기술 스택 추천

플랫폼, 기능, 데이터, 사용자 수, 개인정보, 디자인 제약 및 개발 기간이 충분히 확인된 다음에만 기술 스택을 추천한다.

하나의 정답만 제시하지 말고 필요한 경우 다음과 같이 최대 2~3개의 대안을 비교한다.

- 권장안
- 더 단순한 대안
- 특정 조건에서 적합한 대안

각 대안에 다음 내용을 포함한다.

- 프론트엔드 기술
- 백엔드 기술
- 데이터베이스
- 인증 방식
- 파일 저장소
- 배포 방식
- UI 라이브러리 또는 디자인 시스템
- 외부 서비스
- 테스트 도구
- 선택 이유
- 장점
- 주의점
- 바이브코딩 구현 난이도
- 유지보수 난이도
- 예상 비용 요소
- DESIGN.md 요구사항과의 적합성

다음 원칙을 적용한다.

- 사용자가 이미 알고 있는 기술을 고려한다.
- 개발 기간과 예산을 고려한다.
- 학교의 기기와 네트워크 환경을 고려한다.
- 유지보수 담당자의 기술 수준을 고려한다.
- 소규모 프로젝트에는 단순한 구조를 우선한다.
- 필요하지 않으면 마이크로서비스나 Kubernetes 같은 복잡한 구조를 제안하지 않는다.
- 모바일 앱이 꼭 필요하지 않으면 반응형 웹앱이나 PWA가 적절한지 검토한다.
- 네이티브 기기 기능이 중요하면 모바일 앱이나 데스크톱 앱을 고려한다.
- 초보자 프로젝트에는 관리형 서비스를 대안으로 제시한다.
- 특정 기술이나 제품을 무조건 권장하지 않는다.
- DESIGN.md에 특정 UI 라이브러리가 지정되어 있으면 기술적 적합성을 검토한다.
- 정확한 최신 버전, 가격, 무료 한도 또는 서비스 정책이 중요하면 공식 문서 확인 필요성을 표시한다.
- 변하는 버전·가격·한도·정책을 확정적으로 제시하려면 공식 자료로 확인한다. 확인할 수 없으면 확인 필요로 표시한다.

## 파일·연동·동기화·운영

- 실제 업로드 기능이 있으면 파일 저장소를 고려한다. 소유자, 크기·형식 제한, 비공개 접근·다운로드, 보관·삭제와 DB의 메타데이터 관계를 정한다.
- BaaS는 운영 방식으로 관계형/NoSQL과 별도의 선택 축이다. 관리형이어도 권한 정책·저장 지역·비용·백업 책임을 확인한다.
- 외부 API마다 호출 주체·입출력·인증·오류·호출 제한·비용·개인정보를 정한다. 비밀키는 서버 환경변수나 비밀 저장소로 관리하고 브라우저 번들에 넣지 않는다.
- 화면에서 버튼을 숨기는 것만으로 권한을 보장하지 않는다. 서버나 BaaS 정책에서 사용자·학교·학급 경계를 검사한다.
- 오프라인 기능 범위, 기기 저장 자료, 온라인 복귀 시 동기화, 중복·충돌, 재시도를 정한다. PWA 기능은 기기·브라우저에 따라 지원 범위를 확인한다.
- 정적 도구는 정적 호스팅, 서버 기능은 서버/관리형 서비스, 내부망은 기관 배포 경로, 설치 앱은 서명·설치·업데이트 담당자를 검토한다. 계획 작성은 실제 배포 허가가 아니다.
- 초보자 구현 난이도는 설치·계정 수, 코드 구성요소, 인증·권한, 동기화, 배포·운영 부담으로 낮음/중간/높음과 근거를 제시한다.
- 요구에 없는 실시간 협업·동기화·인증·DB를 추가하지 않는다. 개인 로컬 도구의 백업은 파일 내보내기로 충분한지도 검토한다.
