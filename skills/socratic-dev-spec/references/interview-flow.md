# 문답 진행 가이드

질문 후보는 설문지처럼 제시하지 말고 현재 답변으로 결정이 달라지는 것만 선택한다.

## 문제와 사용자 발견

첫 단계에서는 기술을 묻지 않고 해결할 문제와 사용자를 파악한다.

필요에 따라 다음 내용을 확인한다.

- 누가 사용하는가?
- 언제, 어디에서 사용하는가?
- 현재 겪고 있는 불편은 무엇인가?
- 지금은 그 문제를 어떻게 해결하는가?
- 기존 방법에서 가장 불편한 점은 무엇인가?
- 프로그램을 통해 무엇이 더 쉬워져야 하는가?
- 성공 여부를 어떻게 판단할 수 있는가?
- 교사, 학생, 학부모, 관리자 중 누가 사용하는가?

처음부터 모든 항목을 묻지 않는다. 가장 중요한 질문부터 시작하고 답변에 따라 후속 질문을 선택한다.

스킬이 호출되면 긴 설명이나 전체 질문 목록을 보여주지 말고 다음과 비슷하게 시작한다.

“좋습니다. 제가 한 번에 한 가지씩 질문하면서 아이디어를 실제로 만들 수 있는 개발명세서로 정리해 드릴게요. 기술을 잘 모르셔도 괜찮습니다. 먼저, 어떤 사람이 어떤 상황에서 겪는 문제를 해결하는 프로그램을 만들고 싶으신가요?”

사용자가 이미 아이디어를 자세히 설명했다면 이를 반복해서 묻지 않는다. 사용자의 설명을 짧게 요약하고 가장 중요한 미확인 사항부터 질문한다.

## 핵심 사용자 행동 발견

사용자가 프로그램을 실행한 순간부터 목적을 달성할 때까지의 과정을 질문한다.

필요에 따라 다음 내용을 확인한다.

- 사용자가 처음 보는 화면
- 사용자가 가장 먼저 하는 행동
- 사용자가 입력하거나 선택하는 정보
- 프로그램이 처리해야 하는 내용
- 사용자에게 보여주는 결과
- 결과를 저장해야 하는지
- 결과를 인쇄, 다운로드 또는 공유해야 하는지
- 잘못 입력했을 때 수정할 수 있어야 하는지
- 작업에 실패했을 때 어떤 안내가 필요한지
- 관리자용 기능이 필요한지
- 반복해서 사용하는 기능이 무엇인지

처음부터 화면 목록을 요구하지 않는다. 핵심 사용자 흐름을 파악한 다음 필요한 화면을 도출한다.

## 특별한 상황에 따른 질문 분기

- 동기화
- 백업
- 권한 관리

- 동시에 수정할 수 있는지
- 수정 기록이 필요한지
- 역할별 권한
- 충돌 처리
- 알림 필요 여부

## 학생 개인정보가 포함되는 경우

다음을 추가로 확인한다.

- 꼭 수집해야 하는 정보
- 열람 가능한 사용자

- 자료 보관 기간
- 삭제 방식
- 외부 서비스 전송 여부
- 기관 정책 확인 여부
- 가상 데이터로 시제품을 만들 수 있는지

## 오프라인 사용이 필요한 경우

- 오프라인에서 사용할 기능
- 온라인 복귀 후 동기화
- 데이터 충돌 처리
- 현재 기기에 저장해도 되는 정보

## 외부 AI 서비스를 사용하는 경우

다음을 추가로 확인한다.

- AI가 처리할 입력
- 개인정보 포함 여부
- 개인정보 또는 식별정보를 제거할 수 있는지
- AI 결과의 정확성 검토 방법
- 잘못된 결과의 처리
- API 비용
- API 키 보호
- 사용자가 AI가 생성한 결과임을 알아야 하는지

- PDF, 문서 또는 스프레드시트 중 필요한 형식
- 학교 양식 유지 여부
- 인쇄 용지 크기
- 한글 글꼴
- 표와 페이지 나눔
- 개인정보 표시 범위

## 앱스토어 배포가 필요한 경우

다음을 추가로 확인한다.

- Android, iOS 또는 둘 다인지
- 개발자 계정 보유 여부
- 심사와 업데이트 담당자
- 개인정보 처리방침
- 푸시 알림
- 앱 권한

## 비기능 요구사항 확인

프로젝트에 관련 있는 항목만 질문한다.

- 예상 사용자 수
- 동시에 접속하는 사용자 수
- 원하는 응답 속도
- 모바일 화면 지원 여부
- 지원 브라우저와 운영체제
- 오프라인 사용 여부
- 접근성 요구사항
- 저사양 기기 지원 여부
- 다국어 지원
- 백업과 복구
- 오류 기록과 추적
- 유지보수 담당자
- 개발 기간
- 예산
- 무료 서비스 사용 필요 여부
- 배포 방법
- 업데이트 방법
- 테스트 수준

실제 예상 사용자 수와 사용 패턴에 비례하여 설계한다. 성능이나 확장성을 막연하게 최대 수준으로 설계하지 않는다.

## MVP 범위 결정

사용자가 요청한 기능을 다음 세 범주로 분류한다.

- 반드시 필요한 핵심 기능
- 있으면 좋은 기능
- 첫 버전에서는 제외할 기능

기능이 너무 많으면 다음과 같이 질문한다.

“이 프로그램을 처음 공개했을 때 사용자가 단 한 가지 일만 성공적으로 할 수 있다면 무엇이어야 할까요?”

교사 연수처럼 개발 시간이 제한된 경우 핵심 사용자 흐름 하나가 처음부터 끝까지 작동하는 최소 기능 제품을 우선 제안한다.

MVP 범위를 정할 때 다음을 함께 고려한다.

- 연수 또는 개발 시간
- 사용자의 개발 경험
- 실제 배포 여부
- 시연용 시제품인지
- 개인정보 포함 여부
- 외부 서비스 연결 여부
- 유지보수 담당자

## 최종 명세서 작성 전 확인

개발명세서를 작성하기 전에 다음 내용을 짧게 요약하여 사용자에게 확인받는다.

- 해결하려는 문제
- 주요 사용자
- 핵심 사용자 흐름
- 실행 플랫폼
- MVP 핵심 기능
- 백엔드 필요 여부
- 데이터 저장 방식
- 로그인과 권한
- 개인정보와 보안 고려사항
- DESIGN.md 제공 여부
- DESIGN.md의 필수 디자인 원칙
- 기능과 디자인 요구사항의 충돌 여부
- 접근성 요구사항
- 모바일과 데스크톱 중 우선할 화면
- 추천 기술 스택
- 아직 가정으로 남아 있는 사항

결과를 크게 바꿀 수 있는 미결정 사항이 있으면 한 번 더 질문한다.

중요하지 않은 세부사항은 합리적인 기본값을 사용할 수 있지만 반드시 `가정`으로 표시한다.

## 질문 종료 조건

다음 조건이 충족되면 질문을 종료하고 개발명세서를 작성한다.

- 해결할 문제가 분명하다.
- 주요 사용자가 확인되었다.
- 핵심 사용자 흐름이 확인되었다.
- 실행 플랫폼을 판단할 수 있다.
- MVP 범위가 결정되었다.
- 데이터 저장 필요 여부를 판단할 수 있다.
- 백엔드 필요 여부를 판단할 수 있다.
- 로그인과 권한 필요 여부를 판단할 수 있다.
- 개인정보 또는 보안 위험이 확인되었다.
- 디자인 방향을 설명할 수 있다.
- DESIGN.md가 있다면 핵심 원칙을 분석했다.
- 기술 스택을 추천할 수 있다.
- 구현 완료 여부를 확인할 인수 조건을 작성할 수 있다.

모든 세부사항이 완벽하게 결정될 때까지 대화를 불필요하게 끌지 않는다. 중요하지 않은 사항은 가정으로 표시하고 명세서를 완성한다.

## 적응형 진행 예시

- 저장 없는 개인용 타이머라면 공동 편집·계정·DB 질문은 생략하고 주 기기와 설치 제약으로 넘어간다.
- 여러 교사가 학급 기록을 공유한다면 조회만 하는지 공동 수정인지 물은 뒤 권한·동시 수정·충돌·백업으로 이어간다.
- Windows 교실 PC라면 설치 권한·프린터·내부망, 모바일이라면 기종·기기 기능·스토어, 브라우저라면 학교 접근 제한을 우선 확인한다.
- 완전 오프라인과 외부 AI의 상시 응답이 함께 요구되면 연결 없이는 외부 호출이 불가함을 설명하고 기능별 우선순위를 묻는다.
- 모른다는 답에는 일상 사례와 2~4개 선택지를 주며 비용·난이도·편의 차이를 설명한다. 빠른 진행에는 가정임을 표시한 기본값을 제안한다.
- 중간 요약은 '확정: … / 가정: … / 결정 필요: …'로 짧게 쓰고 다음 질문 하나로 이어간다.
- 기본 아이디어·사용자 파악 후 DESIGN.md를 한 번 확인한다. 접수와 나중 제출 처리는 [design-intake-guide.md](design-intake-guide.md)를 따른다. 나중에 받기로 했다면 디자인은 가정으로 남기고 기능 문답을 계속한다.
- 이미 제공된 답변, 불필요한 기능, 기술·명세 결정에 영향을 주지 않는 질문은 건너뛴다. 사용자가 지금까지 내용으로 작성을 요청하면 최종 확인 대기 없이 작성한다.
